# RO-Crate  Photos Specification

## 1. Purpose and Scope

This application is designed to maintain "at rest" collections of imgages and metadata about them including phorographs and scans on a filesystem using nested RO-Crate packages (in a structure that is, by default, only two levels deep). Irocrate allows Where possible, metadata is synchronised between images and the RO-Crate structure, but it allows for another layer of descriptive data that ties images together, with data about people and other agents, events and so on.

The point of having the RO-Crates, with HTML views, is to provide a standards-based mechanism to describe collections, so that a 'parked' collection has basic navigation built it and important metadata, as defined by the collection's custodian(s), is avaiable without having to use any kind of application. The entire system functions with just an web browser to click around, view the collection by date, subject and whatever other metadata fields are chosen for the main navigation. 

The application adds RO-Crate HTML sites  crate hierarchy to provide static navigation through the collection, including basic configurable finding aids by time, subject, and image properties such as camera used (including people in the pictures and as photographers).

Key feratures:
- Stand-off annotation of images with keywords, face regions etc
- Optional writing-back metadata to images for interop with other tools in the future
  - In place
  - On export 

## 2. Data Model

### 2.1 File structure

The data structure is as follows:

1. The root of the collection is an RO-Crate (it has an `ro-crate-metadata.json` file). 
2. Nested under this there is another layer of RO-Crate files that contain sub-collections, which are typically a directory of files, a day's photos, an upload from a camera in a single directory, or a set of scanned images, these may occur at any depth below the root but do not contain any further ro-crates. This accounts for typical ways of ordering image collections which may be scaffolded by date-based (/yyyy/mm/dd/) upload-from-camera-based or subject based approaches.

3. Crate depth is capped at two levels by default: the root crate and its immediate sub-collection crates. Sub-collection boundaries are determined by a top-down filesystem walk from the root: the first directory encountered that contains an image file becomes a sub-collection crate. Any further nested directories and images beneath that point, regardless of depth, are absorbed into that same sub-collection crate rather than becoming crates of their own.

There's a _rocphotos directory with config/ and trash/ and backup/ directories (backup to be implemented later)

### 2.2 RO-Crate data

Multiple kinds of RO-Crate exist in a scanned collection, each its own standalone `ro-crate-metadata.json` — a crate never depends on another crate's file to be a complete description of what it directly contains:

- **The root crate**, one per collection, at the collection's own root directory: a `Collection` entity (PCDM's `http://pcdm.org/models#Collection`) that mainly exists to anchor the collection and list its sub-collections. In the case where the root directory holds images directly rather than sub-directories (Section 3.1's "Loose Images in the Collection Root"), it also holds `Object` entities the same way a sub-collection crate does, and is treated as the collection's only crate.
  - May also contain ImageGallery (from schema.org, needs no prefix in a crate) entities which are virtual collections of images
- **Sub-collection crates**, one per sub-collection directory (Section 2.1) — also a `Collection` entity, `memberOf` the root — holding the actual `Object` entity per photo/scan in that directory: its EXIF-derived metadata (camera, lens, dates, keywords, rating), and an `ImageRegion` entity for every named face/pet box tagged on it, each pointing to a shared `Person`/`Pet` entity (Section 3.2). A `Person`/`Pet` depicted across several sub-collections is duplicated into each one that depicts them, rather than defined once and referenced from the rest — "the RO-Crate way."
- **The faces crate** (`_rocphotos/faces/ro-crate-metadata.json`), a single crate outside the root/sub-collection hierarchy, holding one `FaceEmbedding` entity per confirmed face-recognition reference example (Section 3's Face Recognition). Each points back to the real `ImageRegion`/Person it came from rather than duplicating any image data, so it stays just a mirror, for inspectability — matching and review actually query its companion SQLite file, `_rocphotos/faces/faces-index.sqlite`, not this crate. There may be other similar data in the future for other kinds of objects.

The main SQLite index (`rocphotos-index.sqlite`, Section 3.2) is a queryable, read-only collection of the root crate and every sub-collection crate combined — the faces crate and its own SQLite file are a separate, parallel pair, not folded into this index.


## 3. Application Behaviour

On opening, the application scans the file tree and creates/updates a confif file with a view of the file system which is presented to the user so they can select a directory to work on, say a day, year, month of files at a time as adding data can take a while (as with all large scale photo managers). This config is saved, so the users sees a tree - map of where there are sub-collections (as defined in the data model), slect which ones to scan, if the crates are out of date (something has changes) and whether scanning is complete (marked by the app when it creates). Re-opening the app will find this config/map and open it.

Once the user has seent the overview and selected all folders or a subset to describe the app utomatically creates the root crate and sub-collection crates, traversing the directory structure and adding Image entities to the sub-collections if they are not already present. It also stores thumbnails in a subdirectory. Non-image files encountered during the walk are ignored and are not added to the crate.

The overview/map is `rocphotos-overview.json`, at the collection root: one row per sub-collection (its path, image count, and status — `not-scanned`, `out-of-date`, `up-to-date`, or `invalid` — a sub-collection whose existing crate file is not a loadable RO-Crate at all, e.g. one authored by a different, incompatible tool; reported rather than thrown, the same tolerance `scanCollection.js` below has for the actual scan). Status is decided cheaply — a directory walk plus one file-modification-time check per image — without reading any image's actual bytes or its existing crate's EXIF data, since that is the expensive part (EXIF extraction and thumbnail generation) this screen exists to let the user defer for a large, decades-spanning tree. A sub-collection already up to date is shown but not pre-selected, since there is nothing to gain from processing it again; "Refresh Status" recomputes the map on demand (for example, after files have changed on disk outside the app) without processing anything. A sub-collection with no crate yet that is left unselected is not added to the root's navigation until it is; one already scanned but left unselected on a later run keeps its existing place in the root's navigation, read cheaply from its own existing crate rather than reprocessed. The "Always process everything on open" checkbox (browser SPA only — Section 4.1) bypasses this screen entirely, for a small collection where the up-front status check has no value.

**The same screen, shared code, in `rocphotos serve` (desktop mode).** Originally only the browser SPA had this — `rocphotos serve` required a collection to already have been scanned via the CLI first, refusing to even start otherwise. It now bootstraps instead (`bootstrapCollection` in `scanCollection.js`, called unconditionally, and idempotently, at `serve` startup): an empty root crate and a default `rocphotos.config.json` are created if neither exists yet, so a directory that has never been touched by this app at all can be pointed at directly. The web view then gets its own "Scan Collection" button (next to Select All in the status bar), opening the exact same tree — checkboxes, status badges, Select All/None, Refresh Status, Process Selected — as a full-screen panel; it opens itself automatically, with no click needed, the first time it finds every sub-collection still `not-scanned` (a fresh bootstrap), so a brand new collection always has an obvious next step instead of a silently empty grid. The tree-building and rendering logic itself (`buildOverviewTree`, and the DOM rendering/checkbox-selection functions built on it) lives in `webview/overviewUI.js` and is imported, unchanged, by both pages — the browser SPA's `src/main.js` (by its real path on disk; see vite.config.js's own note on why `webview/` is never bundled) and `rocphotos serve`'s own `webview/app.js` (as a plain, unbundled ES module, the same way every other file under `webview/` is served) — only how an overview is obtained and a selection actually processed differs: an in-browser File System Access API walk for the SPA, versus two small routes on the already-running server (`GET /api/admin/overview`, `POST /api/admin/scan` — `src/core/admin/handler.js`) for `rocphotos serve`. A server-triggered scan runs against the same long-lived `db`/`fsAdapter` the rest of `serve` already holds (`scanCollection` in `scanCollection.js` — the same core `bin/rocphotos.js`'s own CLI `scan` command now delegates to, so the CLI and the admin screen can never drift into two different scanning implementations), serialized through the same write queue a face confirmation uses (`writeQueue.js`), and clears the AROCAPI handler's shared crate-read cache afterward — so a scan triggered from the admin screen is reflected immediately in the grid, facets, and Collections panel, with no server restart.

The persisted file is this flat list, but the screen itself renders it as a collapsible tree of the directory structure above each sub-collection (a year, then a month, say, though the shape is whatever the collection's own layout is) — a flat list of every sub-collection does not scale to a collection spanning many years. The tree is rebuilt from the flat list in memory each time it is shown; nothing beyond the flat list is persisted. Every folder is collapsed by default and shows a summary of its own status counts (how many of the sub-collections nested beneath it, at any depth, are not scanned, out of date, or up to date) without needing to be expanded; only a sub-collection itself (a leaf of the tree, never an intermediate folder) is ever actually selected for processing, but checking a folder selects everything beneath it at once, and a folder's own checkbox shows an indeterminate state when only some of its descendants are selected. Expanding a folder to look inside it, or a selection made within one, survives "Refresh Status" and processing — neither rebuilds the tree from a blank, fully collapsed state.

The application extracts EXIF metadata from images and adds it to the sub-crates (user can configure this, and a config file is kept at the root, app has a UI for mangaing it). If EXIF extraction for a given image fails or produces malformed data, the image is still added to the crate; the error is recorded in the `processingError` property of the image's `ImageObject` entity rather than causing the image to be skipped. A thumbnail generation failure (see Section 3.3) is recorded the same way; if both an EXIF error and a thumbnail error occur for the same image, both are combined into that one `processingError`, so a file's full error state — used for both the retry logic below and for surfacing "this file has a problem" in the generated HTML preview — lives in one place, in the crate itself, rather than a separate log. `processingError` is unrelated to `description` (an earlier version of the application used `description` for this, which meant a real caption and a processing error could never coexist — see the Editing section's title/description below).

Two further, purely descriptive properties are also extracted, both editable (see Editing): `title` (IPTC `ObjectName` / XMP `dc:title`) always has a value — the image's own title if it has one, its filename otherwise, so it is never blank — and `description` (IPTC `Caption-Abstract`, keyed `Caption` in the `exifr` library's own IPTC dictionary — not the literal IPTC field name — / XMP `dc:description`), a free-text caption with no fallback, simply absent when the file has none. Confirmed against real files: some cameras (Olympus, at least) write a boilerplate value here ("OLYMPUS DIGITAL CAMERA") on every photo rather than a real caption, extracted the same as any other value — telling that apart from an intentional caption is left to whoever reviews or edits it, not solved automatically.

Reprocessing an image (re-reading it, re-extracting EXIF, and re-attempting a thumbnail) is skipped on a rescan if the source file's modification time has not changed since it was last processed — recorded as the `dateModified` property on the image's `ImageObject` entity — regardless of whether that previous attempt succeeded or recorded an error. This means a file that failed once (an unsupported format, corrupt data) is not retried on every subsequent scan; it is retried only once the file itself changes (for example, replaced with a working copy), keeping a rescan of a large, mostly-unchanged collection fast. The same skip also means that adding a new kind of extraction to the application itself (a new EXIF field, say) does not retroactively apply to files already scanned before that change, since their source files have not changed — the CLI's `--reprocess` flag forces every file to be re-read and re-extracted regardless of modification time, for exactly this case.

`rocphotos scan <directory> --subdir=<name>` (repeatable) restricts scanning to just the named sub-collection(s) — and everything nested under them — rather than the whole tree in one pass, for indexing a large, decades-spanning collection incrementally. Every other sub-collection is left entirely untouched this run (its existing `ro-crate-metadata.json`, if any, is not even read), and still contributes to the root's own preview page and `hasPart` list from whatever the SQLite index already recorded about it in an earlier run — a sub-collection never yet scanned at all simply has nothing to show yet, the same as before this flag existed. Scanning also tolerates one sub-collection's existing crate file failing to load — confirmed against a real, foreign RO-Crate (authored by Describo, whose descriptor node uses a nonstandard id the `ro-crate` library's own root-dataset lookup does not recognise, so it throws `There is no pointer to the root dataset`) sitting inside an otherwise-unrelated part of the tree: rather than aborting the entire scan, that one directory is reported and skipped, left untouched exactly like an unselected `--subdir`, and everything else scans normally.

The application also maintains a SQLite index of the collection, organised as per the [AROCAPI specification](https://github.com/crate-works/ro-crate-api). See Section 3.2.

### 3.1 Excluding Directories and Files from the Walk

Certain directories must never be treated as, or searched within for, a crate. Dotfiles and dot-directories (`.git`, editor and OS metadata, and similar) are excluded by default, since they are near-universal filesystem noise unrelated to photo storage. The application's own generated `thumbnails/` cache directory (see Section 3.3) is always excluded, regardless of configuration, since including it would cause the application to mistake its own output for source images on a later scan.

Beyond these, a collection may contain directories, or individual files, that are not part of the application's default exclusions but should still never be scanned — for example, a static HTML gallery previously exported by another tool, sitting inside what is otherwise a legitimate day-of-photos directory, or a handful of stray images sitting loose in the collection root. To handle this, the application reads an optional `rocphotos.config.json` file from the root of the directory being scanned:

```json
{ "excludeDirectories": ["^\\.", "^HTML"], "excludeFiles": ["^Thumbs\\.db$"] }
```

`excludeDirectories` and `excludeFiles` are each a list of regular expressions, tested against a directory's or file's own name (not its full path), at any depth in the walk; a file matching `excludeFiles` is treated as though it were not there at all, both as a possible crate-triggering image and as a member of whichever crate it would otherwise belong to. When present, `excludeDirectories` is used in place of the built-in dotfile default, so a configuration that still wants dotfiles excluded restates that pattern explicitly, keeping the effective stop-list fully visible in one place; `excludeFiles` has no built-in default; there is no filename pattern that is universally junk. This file is read through the same filesystem interface as everything else, so it is honoured identically by the command-line tool and by the browser SPA, which can only read files inside the directory the user has granted it access to.

The same file also holds `writeMetadataToFiles` (boolean, default `false` when absent or the file itself does not exist), the one setting controlling whether confirming a recognized face is allowed to write into the original photo file at all (see the Face Recognition section's "Writing to the original file is off by default" — `loadWriteMetadataToFilesSetting`/`setWriteMetadataToFilesSetting` in `config.js`). Set via a checkbox on the Settings section of the initial screen (Section 4.1), not by hand-editing the file, though nothing stops a config author from doing so alongside `excludeDirectories`/`excludeFiles`.

#### Loose Images in the Collection Root

Because the first directory encountered in the top-down walk that directly contains an image becomes a crate boundary (Section 2), an image file sitting loose directly in the collection root — alongside otherwise-legitimate year/month/day subdirectories — would make the walker treat the whole root as the sole crate, silently absorbing every subdirectory beneath it and hiding all of their crates. (This does not apply when the root directly holding images is the *only* content: that is the intended single-folder-collection behaviour described in Section 2, not an ambiguity to resolve.)

When the command-line tool detects this situation it lists the loose image files found and interactively asks the user to either move them into a new folder — prompting for a name, defaulting to `images` (or `images-2`, `images-3`, and so on, if the chosen name is already taken) — so they become an ordinary sub-collection crate, add them to the config's `excludeFiles` list so they are ignored on this and every future scan, or cancel the scan so nothing is touched. This interactive prompt requires a real terminal; it is not attempted when standard input is not a TTY.

The same resolution is also available non-interactively, for scripted use or once the user already knows what they want: `rocphotos scan <directory> --loose-root-images=move [--loose-root-images-folder=<name>]` or `--loose-root-images=ignore`, which resolves the situation immediately without prompting.

The browser SPA does not yet offer either the interactive prompt or the command-line flags; it currently just honours whatever `excludeFiles` the config already contains.


 ### Editing

 The web view (Section 3.2 — `rocphotos serve`, and the browser SPA's own Service-Worker-backed copy of it) can be used to edit metadata, not only browse it. This is a second writer to the crate JSON and the index, the same two places scanning itself writes to — not a write path added to AROCAPI's own read/search endpoints (Section 3.2's AROCAPI Endpoints subsection), which stay read-only.

 Each grid tile has a checkbox, and a "Select All" control selects every tile the current search has on screen (there is no pagination yet for "all" to mean more than the search's own 200-result cap). A selection bar appears once one or more are checked, offering bulk actions (the same actions are also available for just the one photo currently open in the full-screen viewer, as a single-image case rather than a separate code path):

 - **Delete** — moves the source file into `_rocphotos/trash` (Section 2's data model), preserving its original path beneath that directory rather than deleting it outright, and removes it from the crate and the index. Its thumbnail file is deleted outright (thumbnails are always regeneratable, nothing is lost); a Person/Pet entity it depicted is left alone, since another photo may still depict them.
 - **Add keyword** — a small dialog lets several keywords be added in one go: type one, press the (+) button (or Enter) to add it to the list, repeat, then submit; the whole list is applied together in one edit. Existing keywords (every distinct value already used anywhere in the collection) are suggested two ways: a native autocomplete dropdown on the text field, and an always-visible, click-to-add list beneath it that narrows as you type — both driven by the same `POST /search` with `facets: ['keyword']` and no filters the sidebar's own Keywords facet already uses, fetched fresh each time the dialog opens. A collection this size does not need a dedicated autocomplete/typeahead endpoint for this; AROCAPI has no such primitive (only a full facet-value dump via search), which would be worth raising with the AROCAPI/CrateWorks project if a collection ever grew large enough that fetching the whole vocabulary stopped being practical.
 - **Remove keyword** — removes one keyword across every selected image.
 - **Set rating** (bulk, from the selection bar) — sets a 1-5 star rating across every selected image, or clears it if left blank. A single image's own rating is instead set directly: a row of five stars is shown just below its thumbnail in the grid and below the full-size image in the viewer — outlined for every position above the current rating, filled at and below it — and clicking a star sets the rating to that position, or clears it if it already matches the current rating. This needed the entity's own rating added to `GET /entities`/`POST /search`'s entity JSON (not an AROCAPI property — an application-specific addition, the same way `/entity/{id}/thumbnail` already is), so the grid can show every tile's rating without a separate metadata request per tile.
 - **Edit title** / **Edit description** — single-image only, from the viewer (a title or caption naming one specific photo makes little sense set identically across a bulk selection, unlike a keyword or a rating). The grid caption and the viewer's own heading show the title, not the raw filename, though the two are identical until a title is actually edited, since title always falls back to the filename otherwise. A blank title resets it to the filename rather than leaving it empty; a blank description simply clears it.

 An edit writes directly to the affected crate's `ro-crate-metadata.json` (via `setImageKeywords`/`setImageRating`/`setImageTitle`/`setImageDescription`/`removeImageEntity` in `crateBuilder.js`) and to the index (`entity_facets` for keywords/rating, plain `entities` columns for title/description, and `entities`/`files` for a delete), and is reflected immediately, without a rescan — the read routes' own crate cache is updated in the same step, not merely left to go stale until the next server restart. Since a rescan only ever re-derives these from EXIF for a file whose modification time has actually changed, an edit survives an ordinary rescan of an otherwise-unchanged file; only `--reprocess`, which forces re-extraction regardless of file mtime, would overwrite it with whatever the file's own EXIF says instead — writing an edit back to the original file's own metadata (not just the crate) would make it survive even that, but that write-back is not yet implemented, pending a decision on the backup mechanism noted in Section 2.

 Face recognition lets people be found and confirmed automatically instead of only via manual tagging in another tool — see Face Recognition below.

 ### Albums (ImageGallery virtual collections)

 The user can create Galleries which are ordered virtual collections of images via a New Album button. This adds an ImageGallery entity to the root crate.

 User can add selected images to the gallery in a similar way to adding keywords via and Add to album button - show the last three albums that have been used and offer a wayt to search for other albums as well.

 Album features (to build one at a time):
 - Create an album — **implemented.**
 - Add images to album, by selecting them first — **implemented.**
 - Export images to an _exports directory, preserving the file-paths they have with or without ro-crate metadata alongside — **implemented, without the metadata part yet** (see below).
 - Create stand-alone HTML album view with an option to include images as datauris for a single-file distribution (option for self-playing slide show, with text overlays) — not yet implemented.

 **Implementation.** An album is a real entity (`ENTITY_TYPE_ALBUM`, `http://schema.org/ImageGallery`) — the same way a Person/Pet is, reusing its existing `name`/`description` columns rather than a parallel table with its own copies of them — keyed by name via `albumEntityId` (same `arcp://` scheme and same name-based identity as `personEntityId`/`petEntityId`, in its own `.../album/` id space so it never collides with a person or pet of the same name). Unlike Person/Pet, which get duplicated into every crate that depicts them, an album's own entity lives only in the root crate (`setAlbumEntity` in crateBuilder.js): a collection-wide concept with no natural "home" crate of its own to also live in. `date_created` doubles as "last used" for an album — bumped both on creation and on every add (`touchAlbum`) — so "recently used albums" (the picker's quick-access list) is a plain `ORDER BY` on a column that already exists, no dedicated one needed.

 Membership is stored *only* in the crate, as the album entity's own `hasPart` (array order is its display order — no separate ordering property, and no SQL table mirrors it): deliberately not duplicated into a parallel index table, since the crate is already the one place this app treats as truth for this kind of relationship, and nothing yet needs to query membership faster than reading one small root crate file allows (there is no `albums` facet — see below). Each `hasPart` entry is not a direct reference to the real image but a small proxy entity, `<albumId>#item-<n>`, of type `ImageObject`, linked to the real image via `prov:specializationOf` (the `prov` prefix is already defined by the standard RO-Crate context every crate references, so this needs no extra `@context` setup) — the same indirection `ImageRegion` already uses to describe an occurrence of a Person without redefining them. The point of the indirection: an image's appearance *in this album* could later carry its own name/description (a caption for how this photo is used here) without touching the real image's own entity, which is shared by every other place that depicts it — not yet settable through any route or UI, but `setAlbumEntity` already never replaces an existing proxy once created (only ever adds a new one for a newly-added image), specifically so that a future caption set directly on a proxy survives every later call to it (adding more photos, editing the album's own name/description). `albumMemberIds` in crateBuilder.js is the one place that reads this back into a plain list of real image ids, for both the write routes and `GET /albums/{id}`.

 Routes (not part of AROCAPI, the same way `/edit/*` above is not): `POST /albums` (create, or update name/description of an existing one with the same name), `GET /albums` (every album, most recently used first, or `?q=` to search by name), `GET /albums/{id}` (name, description, and its members resolved and ordered), `POST /albums/{id}/add` (adds a bulk selection's ids, skipping ones already a member). The web view's "New Album" button (next to Recognize Faces) opens a small name+description dialog; the selection bar's "Add to album" opens a picker of the 3 most-recently-used albums, narrowed by a search box as you type — matching the two UI patterns described above. Neither dialog can create an album inline from the picker: creating and adding are deliberately separate actions, per the "build one at a time" list above.

 `albums` is a real facet (`STORED_FACETS` in `db/store.js`, alongside `people`/`pets`), so an album can be selected the same way as any other facet value and combined with every other active filter (camera, keyword, year, ...) — sorted the grid's usual way (most recent first), same as any other faceted search. Unlike every other facet, it has no source in the file's own EXIF/XMP to derive from at scan time; it is populated by `POST /albums/{id}/add` instead (`addEntityFacetValue` in `db/store.js`, which only ever adds one value rather than replacing an entity's whole set for that facet, since an image can be in more than one album and a single add call only knows about the one it was called for). That route re-syncs the facet for every current member on every call, not only newly-added ones — cheap, since it is a plain `INSERT ... ON CONFLICT DO NOTHING` — so an album whose membership predates this facet (or any future gap in keeping the two in sync) self-heals the next time anything is added to it, confirmed directly against a real collection's own pre-existing album.

 An "Albums" panel in the sidebar (next to Collections) lists every album, including a brand new, still-empty one that would not yet appear in the generic facets panel below (a value with zero matches is never shown there — same as any other facet). Clicking a row is exactly `toggleFilter('albums', name)`, the same as clicking that album's value in the generic Albums facet group below: both are just two ways to reach the one `activeFilters.albums`, not two different features, so a selection made either way is reflected in both (and in the usual removable active-filter chip). An earlier version of this panel bypassed `search()`/`activeFilters` entirely to show an album in its own curated order — replaced once it became clear that not composing with the other facets was the actual complaint, not a missing feature alongside it.

 **Export** (`src/core/export.js`) copies each of an album's member files into `_exports/<album-name-slug>/` at the collection root, preserving each file's own collection-relative path underneath it — a sparse mirror of just this album's files, nothing else (no crate, no metadata; that half of the original feature list entry is still open). `_exports/` is excluded from the scan walk the same way `_rocphotos/` already is (`isSkippedDirectory` in `walker.js`), so an export is never mistaken for a new sub-collection on a later scan. Re-exporting the same album overwrites whatever an earlier export left at the same paths, so it is always safe to just run again after adding more photos.

 Reachable two ways, both sharing this one implementation: `rocphotos export-album <directory> <album name>` (a CLI command, useful without a running server) and `POST /albums/{id}/export` (an explicit "Export \<name\> Album" button in the top bar, next to New Album) — the CLI command reads the index and root crate directly and calls the same `exportFiles`, rather than starting a server just to call its own route. The web view's button only appears while an album is the active `albums` filter (selected either via the sidebar panel or the generic facet group — both set the same `activeFilters.albums`), and is relabelled with that album's own name, so it is never a generic, easy-to-misclick action: an earlier version put a small icon button on every row of the sidebar's Albums panel instead, which was both too easy to click by accident and too small to notice.

 On where exported files end up, and how that differs by run mode (Section 4.1): the destination is always a subdirectory of the collection the handler's own `fsAdapter` already has access to, which resolves the question differently per mode without any mode-specific code. In desktop server mode, that is a real, unrestricted directory on disk, so `_exports/` lands right there under wherever `rocphotos serve` was pointed at. In the browser-only run mode (a Service Worker's `fsAdapter`, backed by the File System Access API), it is a subdirectory of whichever collection directory the user already granted access to when they opened it — needing no extra permission grant, since nothing here writes anywhere the user has not already said yes to. Exporting to an entirely separate location the user picks themselves (their Downloads folder, say) instead of a subdirectory of the collection is a real, distinct feature — it would need a second `showDirectoryPicker()` grant in the browser-only mode specifically — not yet implemented, and deliberately left out of this first cut rather than solved speculatively before anyone asked for it.

 ### Face Recognition

 Extends the existing Person and `ImageRegion` model (Section 3.2 — including that section's Web Annotation-based standoff region shape and its `writtenToFile` flag, the two together being what makes a confirmation fully visible regardless of the "off by default" paragraph below). A confirmed face is always recorded as a standoff region first (`addStandoffFaceRegion` in `crateBuilder.js`, Section 3.2) — a crate-only write, never touching the photo file — and only then, best-effort and separately, written into the photo file's own XMP metadata (via the system `exiftool` binary) exactly as a human-tagged face already is, and re-extracted through the same EXIF pipeline scanning itself uses, superseding the standoff region with the freshly-read one. Whether that second step happens or not, the confirmation itself has already fully succeeded.

 **Library and runtime.** [face-api.js](https://github.com/justadudewhohacks/face-api.js) (TensorFlow.js-based, runs client-side) does face detection and produces a 128-d embedding vector per detected face, loaded from `webview/vendor/` (the UMD bundle and its model weight files, bundled as static assets — see vite.config.js). Because detection and embedding run entirely in the browser, this works the same way in both places the web view runs; `POST /api/faces/confirm` itself now succeeds identically in both, as a standoff region — only the further, best-effort step of writing a region back into the photo file itself needs a real OS process (`exiftool`), so that part alone is only ever attempted from `rocphotos serve` (Section 4.1's desktop mode), never the browser-only Service-Worker mode. Every other route (submitting detections, listing them for review, rejecting a suggestion, Ignore, Ignore as stranger) works the same in both.

 **Writing to the original file is off by default, per collection — but confirming a face never depends on it.** `writeFaceRegion` (`src/adapters/exiftoolWriteback.js`) uses exiftool's `-overwrite_original`, so there is no backup of a file's previous bytes beyond whatever the user's own backups already cover — this file write is otherwise the only thing in this whole app that modifies an original photo file at all (everything else — keywords, rating, title, description, and now a confirmed face's own standoff region — writes only to the crate; see the Editing section above). `/confirm` attempts it only if both `writeFaceRegion` is available (not the browser-only run mode, and exiftool installed) and this collection has opted in (`writeBackEnabled`, read once at `rocphotos serve` startup from `loadWriteMetadataToFilesSetting`, Section 3.1) — neither missing piece, nor the write itself failing (caught and logged, never thrown), turns into a request failure: the standoff region already recorded means the confirmation has already succeeded either way. `createFacesHandler`'s own default for `writeBackEnabled` is `false`, not `true`, so a caller that forgets to pass it (a test, some future integration) fails safe rather than silently writing. The Settings section of the initial screen (Section 4.1) is where this is turned on, per collection, with an explicit warning. Getting `writeFaceRegion` itself fully tested and reliable — and, longer term, factoring its handling of other tools' MWG/XMP quirks (Section 3.2's Person/Pet section already lists a few) out into its own reusable library, rather than growing them ad hoc inside this app — remains ongoing work independent of this default.

 **Where reference data lives.** A dedicated crate, `_rocphotos/faces/ro-crate-metadata.json`, holds reference examples — one `FaceEmbedding` entity per confirmed face embedding, for inspectability. Each one records: the Person it is for (or no Person at all — see Ignoring as a stranger, below), the id of the real `ImageRegion` it came from (so it can always be re-cropped from the original photo on demand; no image data is duplicated), the embedding vector itself, and the name and version of the model that produced it, supplied by the browser (the actual source of truth for which model ran) and never assumed by the server. A companion SQLite file, `_rocphotos/faces/faces-index.sqlite`, is what matching and review actually query — the crate above is a mirror, not consulted at request time. It tracks: `scanned_images` (which images have been face-scanned already, keyed on the same modification-time skip already used for EXIF and thumbnails, so re-scanning a directory does not reprocess unchanged files, and a changed model name/version forces a re-scan), `reference_faces`, and `detections` (each with its status: `pending`, `confirmed`, `ignored`, or `auto_ignored`). Matching a new detection against the reference set is done in memory by comparing embeddings directly (Euclidean distance, face-api.js's own recommended 0.6 threshold), not as a SQL query — a personal collection's reference set is small enough that this needs no vector-search infrastructure.

 **Browsing by directory.** Finding faces defaults to whatever the grid currently shows — normally one directory at a time, via the web view's "Collections" panel (Section 3.2's AROCAPI Endpoints and the Web View) and its `memberOf` filter, but any other combination of active filters works identically, since "batch" just means "the current search result."

 **Learning from already-tagged faces.** A face tagged by another tool (digiKam, Lightroom, Apple Photos) or confirmed in an earlier rocphotos session already has a name and a box but no embedding of its own — without a separate step, the reference set would start empty and never learn about it, so even someone tagged throughout the whole collection would get no suggestions on the very first run. This backfill runs over every image in the whole collection, regardless of the current directory/filter — unlike finding new faces (below), which is deliberately scoped to the current view, learning from an existing tag is one-time, collection-wide bookkeeping that should not depend on which directory happened to be open.

 An image whose every named region already has a reference, as of its exact current file mtime, is skipped without even reading its crate (`backfill_checked_images`, checked via `isBackfillFullyChecked` — the same mtime-keyed pattern `scanned_images` already uses for detection). Without this, every single "Recognize Faces" click re-examined every tagged image in the whole collection from scratch, even ones nothing had changed about since the last click — which is what made this step feel like it was permanently redoing work it had already done, even once it stopped actually duplicating anything. An image is only ever marked fully checked once none of its regions were left needing a reference on that pass (or, since a genuinely undetectable one is never going to resolve on some later pass either, once every remaining region has been marked undetectable — see below); one with an embedding that failed to compute and has not yet been reported as undetectable is left unmarked, so only that one region — not the whole image — is retried next time, rather than the failure becoming silently permanent. This marking happens the moment an image's last outstanding region is resolved (`markImageIfNowFullyBackfilled`, called from both `/backfill-reference` and `/backfill-undetectable`), not only on some later `/existing-regions` call — confirmed against a real collection that, without this, an image whose final region got resolved partway through one "Recognize Faces" click stayed marked as needing a check for one whole extra click before settling, even though nothing further was actually needed. Confirming a face (writing to the photo file) naturally invalidates this for that image, since its mtime changes.

 `POST /api/faces/existing-regions` lists every already-tagged region not yet backfilled (checked via `hasReferenceForPersonOnImage` — does this Person already have a reference from this image, not whether some region's own computed id matches one already stored, which an earlier, more fragile version of this check did; see below) and not already given up on (`isRegionUndetectable`; see below). For each one, the browser first runs full-image detection (the same method used for finding new faces, matched against the tagged region's own box) and, only if that finds nothing there, falls back to a generously-padded crop zoomed on just that region, detected at a much lower confidence threshold than normal detection ever uses. The fallback matters: confirmed against a real, small background face in a group photo that whole-image detection missed outright (face-api.js downscales the whole image internally, and a small face can end up too tiny to recognize, or score below the default confidence cutoff even when technically found) — a lower threshold is safe here specifically because a human already confirmed a face is exactly in this tight crop, so there is nothing else in it to misattribute a detection to. Whichever one succeeds, `POST /api/faces/backfill-reference` records its embedding as a reference example — no review step, since a human already confirmed the name.

 A named region's `Area` (MWG's own convention, fractional and center-based — Section 3.2) is compared against a detected face both as-is and after correcting it for the file's own EXIF Orientation (`correctAreaForOrientation` in `src/core/faces/orientation.js`) — both, not just one: different tagging tools disagree about which frame `Area` is measured against for the very same Orientation value. Confirmed against two real files: a digiKam-tagged one needs the correction to line up with a real detection; an Apple Photos-tagged one (identifiable by its `XMP-apple-fi` region extension) already matches without it, and applying the correction moves the box to a different part of the photo entirely, causing the same already-tagged face to be re-detected as new on every run. `bestOverlapEitherOrientation` in `src/core/faces/geometry.js` tries both and uses whichever one actually overlaps a real detection, rather than guessing which convention a given file's author used. The overlap measure itself (`containmentOverlapRatio`) is intersection over the area of the *smaller* of the two boxes, not plain intersection-over-union (`boxOverlapRatio`, kept for other uses) — needed because different tools draw a face box at genuinely different scales for the very same face, not just a different position: confirmed against a real file where face-api.js's own detection of a face was well-centered on a digiKam-tagged region but roughly half its linear size (a tight box around facial features vs. one including more of the head), which plain IoU scored at ~0.10 — comfortably below any reasonable "same face" threshold — while the containment measure correctly scored it around 0.36.

 **Giving up on a genuinely undetectable face.** Even with the crop fallback above, some already-tagged faces are never re-detectable by face-api.js at all — confirmed by inspecting real examples: a full side profile, a face behind sunglasses, one lost to severe motion blur, one in extreme backlighting that blows out most of the frame. Retrying the exact same photo with the exact same model cannot produce a different result, so retrying it forever (and re-reading that image's crate on every single "Recognize Faces" click, since it can never reach "every region has a reference") would just be permanently repeated, pointless work. Once both the whole-image and crop-fallback attempts fail for a region, the browser reports this via `POST /api/faces/backfill-undetectable`, which records it in `backfill_undetectable_regions` (keyed like `reference_faces`, on image/person/model/version — see `isRegionUndetectable`/`markRegionUndetectable`) and is from then on treated the same as a real reference for the purpose of deciding an image is fully checked, without ever being counted as a match anywhere else. A model version bump makes an old row obsolete the same way it does for `reference_faces`, so a future, better model naturally gets its own attempt rather than inheriting an old give-up. The final "Recognize Faces" status line reports how many regions were given up on this run, and every one is queryable directly from `faces-index.sqlite` (`SELECT * FROM backfill_undetectable_regions`), so this is never a silent failure.

 Both the "already backfilled?" listing check and the actual save are idempotent on their own, and need to be: a photo with more than one region for the same Person (duplicate regions — the exact kind of corruption the fixes above produce before they existed, or several detections confirmed for the same face before an early version of the overlap-check below existed to prevent that) all come back in one `/existing-regions` listing, since none of them are backfilled yet at that moment — `/backfill-reference` re-checks `hasReferenceForPersonOnImage` again for itself before saving, rather than trusting the listing's snapshot, so only the first of several duplicates submitted in the same pass is actually saved. `repairMismatchedSourceRegionIds` and `deduplicateReferenceFaces` (both run automatically via `ensureFacesSchema`) clean up reference rows already written under the older, more fragile scheme.

 **Workflow.** The "Recognize Faces" button, next to Select All:
 1. Backfills reference embeddings for already-tagged faces (see above), then loads the face-api.js models on first use, then checks `POST /api/faces/scan-status` for which images currently on screen have not yet been scanned with the current model.
 2. For each of those, runs detection in the browser and submits the results (`POST /api/faces/detections`). Before matching anything, a detected face whose box substantially overlaps an already-named region on that image (`bestOverlapEitherOrientation` in `src/core/faces/geometry.js` — trying both the raw and orientation-corrected form of the region's Area, for the same reason the backfill step above does — comparing against the same already-tagged regions `/existing-regions` reads, via `loadExistingFaceRegions`) is dropped outright, never becoming a detection at all: face-api.js's own detector has no idea an area is already named, so without this, an already-tagged face is detected again as if new, suggested (a near-exact match to the reference it was just backfilled from), and confirming it — especially via "Confirm all" — writes a second, genuinely duplicate MWG region onto the same photo and a second reference for the same (image, Person) pair, every single run. This is what a real collection's `faces-index.sqlite` showed happening in practice: dozens of (person, image) pairs each with exactly one duplicate row. Everything else is matched against the reference set as before: a close match to a Person suggests that name; a close match to a stranger reference (see below) is set to `auto_ignored` and never needs review; anything else is unmatched, still pending review.
 3. Opens a review screen of every pending detection, as a cropped face thumbnail (drawn client-side from the detection's own fractional box, re-cropped on demand rather than cached). Detections with the same suggested Person are grouped into one box together, so a whole batch of easy cases can be handled in one action instead of one at a time; a detection with no suggestion gets its own card under an "Unidentified" heading. Both use the same lookup already built for keywords (a native autocomplete field plus a click-to-fill suggestion list of every known Person) wherever a name is typed, rather than a plain prompt.
    - **Confirm all as \<name\>** — on a match group, accepts every thumbnail still in it (see the per-thumbnail actions below) as that Person in one action. Attempts every one even if an earlier one in the batch fails, and always refreshes the review screen afterward — an earlier version stopped at the first failure without refreshing, which could leave already-confirmed detections stuck looking pending (retrying then failed immediately, since `/faces/confirm` 400s on a detection that isn't pending, before ever reaching the ones after it in the batch).
    - **Reassign all to…** — also on a match group: for when the *whole* group turns out to be the wrong Person, rather than just one face in it. The same lookup, but applied to every detection currently in the group at once.
    - **Reassign** — an inline text field on each thumbnail (in a match group or on its own), pre-fillable from the suggestion list; naming a previously-unmatched face uses the same field. This app identifies a person by name alone (Section 3.2's Person/Pet section), so correcting a suggestion and naming a new person are the same operation — the same name always resolves to the same Person, a new one otherwise.
    - **[-] (reject this suggestion)** — on a thumbnail inside a match group only: says "not this Person" without saying who it actually is, and re-matches that one detection against the reference set with every Person rejected for it so far excluded (`POST /api/faces/reject-suggestion`), rather than merely hiding it from this screen — otherwise the same wrong suggestion would just come back the next time detections are listed. Stays pending under whichever Person it now matches (or none), unless that next match is a stranger reference, in which case it is auto-ignored the same as on first detection.
    - **Ignore** — dismisses this one detection, without writing anything to the photo file or the reference set. Scoped to this exact detection row (a given image, region, and model version), so it is not permanent: a future model version's re-scan of the same image starts with a clean slate for it.
    - **Ignore as stranger** — for a face that is not one of the people this collection is about (a stranger in the background). Adds a reference example with no Person attached; any future detection that matches it closely is set to `auto_ignored` directly, skipping review. The suppressed detection still exists as a row in the faces index rather than being discarded, so what has been suppressed stays visible and reversible.
 4. Confirming (from either "Confirm all" or "Reassign") first records a standoff region (`addStandoffFaceRegion`, Section 3.2) — a crate-only write, `#region-standoff-<n>`-numbered, that alone already makes the confirmation fully visible (viewer tags, "Show faces", `people`/`pets` facets) and updates the index rows (`syncImageIndexFromCrate`) immediately. Only if write-back is available and turned on does it then also attempt a real MWG Face region into the photo file itself (preserving every region already there, including ones from other tools — confirmed safe against a real digiKam-tagged file) and re-extract that one image's EXIF (`rescanImageMetadata`), which supersedes the standoff region with the freshly-read one rather than leaving both — a rescan preserves any *other* standoff region that has no matching freshly-parsed name, so a routine full `rocphotos scan` never silently un-facets someone confirmed this way. Either way, it also adds the detection's embedding as a new reference example, which is how the reference set grows over time — every confirmation is also a new training example, with no separate step. Every crate write here also has to update the AROCAPI handler's own long-lived read cache (`createHandler`'s `crateCache`, shared with the faces handler via its own `crateCache` parameter, both wired up once in `rocphotos serve`) — otherwise `GET /entity/{id}/metadata` (what the viewer's tags and "Show faces" overlay both read) keeps serving whatever it last read for that crate until the server restarts, even though the crate file and the index are both already correct. The response reports `writtenToFile: true/false` so the caller knows which of the two actually happened.

 Not yet implemented: a distinct provenance marker on a machine-confirmed region (so it could be told apart from a human-tagged one at a glance), a UI for inspecting or removing a Person's existing reference examples, grouping the review screen by suggested Person, and re-embedding the reference set after a model upgrade (the storage design above — every reference always links back to its real source region rather than only storing a vector — keeps that possible later without design changes now). Also worth considering: running the backfill step during scanning itself (alongside the existing metadata rescan) rather than only when "Recognize Faces" is clicked, so the reference set is always current without a manual step.

 One known, deliberately unfixed limitation, worth understanding before it is treated as a bug:
 - **A Person's identity is derived from their name, case-sensitively, throughout the whole app** (`nameSlug` in `db/store.js`, used by `personEntityId` — Section 3.2's Person/Pet section), not only for faces: "Jane Smith" and "jane smith" are two different Person entities. For face recognition specifically, this means a name typed into the "Reassign"/"Name this person" lookup with different capitalisation than an existing tag creates a second, separate identity with no error or warning — mitigated somewhat by the lookup's own suggestion list (picking a suggested name reuses its exact existing capitalisation), but not prevented. Making identity case-insensitive would fix this properly, but changes every existing Person/Pet entity id collection-wide, including in already-scanned collections — a real migration, not a quick patch, so it has not been done as a side effect of face recognition work.

### 3.2 The SQLite Index (AROCAPI)

At scan time, the application also builds a SQLite index, `rocphotos-index.sqlite`, at the root of the scanned collection — one database per collection, covering the root crate and every sub-collection crate beneath it (there is no separate index file per sub-crate). This index is a read-only materialised view of what scanning has already written to the crate JSON; it is not a second source of truth, and nothing writes to a crate's `ro-crate-metadata.json` by going through the index.

The schema is a minimal subset of the [AROCAPI specification](https://github.com/crate-works/ro-crate-api), drawn from the [PCDM](http://pcdm.org/models) vocabulary. Every entry point that opens an *existing* index — not only `scan`, which builds one — must call `ensureSchema` on it before using it, the same way `serve` already does for the faces companion index's own `ensureFacesSchema`: confirmed as a real bug while developing the Albums feature (below), when a table added to this schema for an early version of it turned out to silently never exist for an already-scanned collection, because `rocphotos serve` (both the CLI's and the Service Worker's) only ever called `ensureSchema` at scan time. Fixed regardless of that table's own later removal (Albums ended up needing no schema change at all — see below), since the underlying gap was real and would recur for any future schema addition.

- `ro_crates(id, path, name, created_at, updated_at)` — one row per crate directory (the root and every sub-collection crate).
- `entities(id, ro_crate_id, entity_type, name, title, description, processing_error, member_of, metadata_license_id, content_license_id, access_metadata, access_content, date_created)` — one row per crate-as-Collection and one row per image-as-Object. `title`/`description`/`processing_error` are added by `ensureSchema` via `ALTER TABLE` for an index built before they existed, rather than requiring a `--fresh` rescan.
- `files(id, entity_id, filename, media_type, size, relative_path, access_content)` — the actual image bytes backing an Object entity.
- `entity_facets(entity_id, facet_name, value)` — one row per (entity, facet, value) triple, indexed on `(facet_name, value)` and on `entity_id`.

`entity_facets` is a single generic index for every faceted-search field. It treats a facet with several values per entity (keyword, people, pets) and one with at most one (camera, lens, rating) the same way, and adding a new facet is new rows, never a schema change. The current facets, all derived from EXIF/IPTC/XMP at scan time and populated only for image entities, are: `camera` (combines `Make` and `Model`, e.g. "Google Pixel 6a"), `lens` (prefers `LensModel`, since it is typically already a full description such as "Pixel 6a back camera 4.38mm f/1.73", falling back to `LensMake` alone otherwise), `keyword` (from IPTC `Keywords`, XMP `dc:subject`, or the Lightroom XMP extension `hierarchicalSubject`, in that preference order; a hierarchical entry such as `Bird|Nankeen Kestrel` is split on `|` and each level stored as its own separate keyword value, so an image tagged this way matches a search on either "Bird" or "Nankeen Kestrel"), `rating` (the XMP star rating, 1-5; a rating of 0 is treated as no rating at all, since tools such as Lightroom write `Rating: 0` on every photo they touch, not only ones a person actually starred, so it carries no information), and `people`/`pets` (the display name of each named MWG face/pet region on the image — see below). `year` is a further facet derived at query time from `date_created` rather than stored in `entity_facets`, since `date_created` is also used to sort search results and stays a plain column on `entities`. A facet's own currently-selected value never narrows that facet's own counts (only every *other* active filter does), so switching between values of the same facet stays possible. Further facets (events, and so on, once that metadata exists) extend the same table, without any schema change.

Entity types follow PCDM's aggregation model: the root and every sub-collection crate are `http://pcdm.org/models#Collection`; every image is a `http://pcdm.org/models#Object` whose `member_of` points to the `id` of the Collection entity for the crate directory it belongs to. Entity `id` values reuse the same collection-relative path convention already used elsewhere (for example `2025/03/10/` for a sub-collection crate, `2025/03/10/photo.jpg` for an image, `./` for the root), so they are unique across the whole index without needing a separately minted URI scheme.

A named MWG region (a face or pet tagged by an external tool such as Lightroom, digiKam, or Photo Mechanic) becomes its own entity, not only a facet value, so a person or pet can be looked up as a first-class thing in its own right. A `Face` region becomes a `schema:Person` entity; a `Pet` region becomes a `Pet` entity (an application-specific type, since schema.org has no equivalent). Its id is not path-based, since a person is not located at any one place in the collection the way a crate directory or an image is: `arcp://name,rocphoto/person/<slug>` or `.../pet/<slug>`, where `<slug>` is the person or pet's name with whitespace and punctuation stripped — the same name always produces the same id, and a pet and a person who happen to share a name never collide, since they live in separate id spaces. Identity is by name string only: two different real people (or pets) who happen to share an exact name are not distinguished, the same limitation the tagging tool itself has. The entity is recorded in the index once, the first time that name is seen; the same node is then duplicated — "the RO-Crate way" — into every sub-collection crate's own `ro-crate-metadata.json` that depicts them (linked from each image via a `about` property), rather than defined once in a single crate and referenced from others, so that every crate file stays a complete, standalone description of what it contains. A region's name is also written by the tagging tool into the same fields `keyword` is drawn from; once recorded as a Person/Pet entity, it is excluded from that image's `keyword` facet, so the same name is not double-counted under two different facets. exifr does not decode XML character references (`&#39;`, `&apos;`, and the like) inside this nested XMP struct field — confirmed against a real file that a name containing an apostrophe round-trips as the literal text `Alana Mahon&#39;s Daughter`, even though the raw XMP on disk is valid, standard-escaped XML — so `exif.js` decodes these itself for every free-text value read this way (region names, keywords, title, description).

Each occurrence of a region on a particular image is also recorded as its own `ImageRegion` entity (id `<image>#region-<index>`, stable across rescans the same way an EXIF `PropertyValue` node is) — this is what the web view's "Show faces" button (Section 3.2's web view, below) draws. This is distinct from the image's own `about` property (linking directly to the Person/Pet entities it depicts, for the `people`/`pets` facets): a Person/Pet entity is shared and deduplicated across every photo that depicts them, while an `ImageRegion` is specific to one photo's one tagged occurrence of them. `ImageRegion` itself is not a term from any external vocabulary — it, and its current `xPosition`/`yPosition`/`width`/`height` properties (a fractional (0-1), centre-based box, mirroring MWG's own `Area` struct shape), are entirely application-specific, invented for this app rather than adopted from one.

**Standoff region data model.** A confirmed face is recorded using the [W3C Web Annotation Vocabulary](https://www.w3.org/TR/annotation-vocab/)'s own real classes/properties (`oa:`, `http://www.w3.org/ns/oa#` — verified directly against the spec, including its own worked example for `oa:identifying`: an annotation whose target is an image and whose body identifies what it depicts, exactly this shape) instead of the bespoke, file-derived shape above — this is a second, independent region shape, not a replacement for it: a region read from a file's own EXIF at scan time (`regionsFromExif`) still uses the plain `xPosition`/`yPosition`/`width`/`height` shape above; only a region confirmed but not (yet) written into a file — added via `addStandoffFaceRegion` in `crateBuilder.js` — uses this one. `readImageRecord` normalizes both into the same centre-based `{x,y,w,h}` shape for every other consumer, so nothing downstream (the faces handler, the viewer) needs to know which shape a given region actually came from.

```json
{
  "@id": "2025/03/10/photo.jpg#region-standoff-0",
  "@type": ["ImageRegion", "oa:Annotation"],
  "name": "Jane Smith",
  "regionType": "Face",
  "oa:motivatedBy": { "@id": "oa:identifying" },
  "oa:hasTarget": { "@id": "2025/03/10/photo.jpg#xywh=percent:41.6,7.5,29.4,43.75" },
  "oa:hasBody": { "@id": "2025/03/10/photo.jpg#region-standoff-0-body" },
  "writtenToFile": false
},
{
  "@id": "2025/03/10/photo.jpg#region-standoff-0-body",
  "@type": "schema:Person",
  "prov:specializationOf": { "@id": "arcp://name,rocphoto/person/JaneSmith" }
}
```

Two nodes, not one: `oa:hasBody` doesn't reference the shared Person entity directly — it points at a small proxy, `prov:specializationOf` it, the same indirection Albums already use for a member image (Section 3's Albums). Same reason: *this appearance* of Jane Smith, in this one region, could later carry its own region-specific properties without touching the real Person entity every other photo depicting her also references. The proxy's `@type` matches whichever the real entity already is (`schema:Person` or this app's own `Pet`).

`oa:hasTarget` is a bare `{"@id": ...}` reference (as is everything else here — `about`, `memberOf`, `hasPart`, and now this, are all bare id-only references throughout this crate model, never an inline object with its own `@type` or a plain string standing in for one) whose id is the image's own id with a [Media Fragments URI](https://www.w3.org/TR/media-frags/) `#xywh=percent:x,y,w,h` fragment appended — top-left corner + size, as a 0-100 percentage of the full image (not this app's usual 0-1 fraction). Top-left, not centre-based like MWG's `Area`, matching face-api.js's own box convention; the only conversion to MWG's centre convention happens at the point of actually writing a region into a file's XMP (Section 3's Face Recognition). `name`/`regionType` stay as today, plain and unprefixed, duplicated onto the region for the same one-level-resolution convenience they already serve.

**TODO:** `regionType` (`"Face"`/`"Pet"`) is still a bare, unprefixed, application-specific string, not derived from any vocabulary — arguably redundant now with the proxy's own `@type` (`schema:Person` vs this app's own `Pet`), which already carries the same distinction properly. Left as-is for this first pass; worth revisiting once this model is actually implemented, rather than deciding it up front.

`writtenToFile` is this app's own addition, no vocabulary borrowed: `true` for a region read out of the photo file's own EXIF at scan time (it is only known about because it is already there); `false` for one this app has confirmed (Section 3's Face Recognition) but has not — or, per that section's default, not yet been allowed to — write into the file itself. This is the piece this whole model exists to support: a confirmed face becomes fully visible immediately (the viewer's tags, "Show faces", the `people`/`pets` facets) regardless of the file-writeback setting, with actually writing it into the photo file a genuinely separate, later step — unlike a region confirmed via the plain EXIF-derived shape, where the crate learns about it only by re-reading the file `writeFaceRegion` just wrote it into, so disabling that write would leave the confirmation with almost no visible effect at all (Section 3's Face Recognition).

**Implementation.** `addStandoffFaceRegion(crate, path, { name, subjectId, subjectType, box })` (`crateBuilder.js`) creates both nodes above and appends them via `crate.addValues(path, 'regions'/'about', ...)`, which dedupes automatically. Its own id namespace, `#region-standoff-<n>`, is deliberately separate from EXIF-derived regions' `#region-<index>` (which is fully renumbered from scratch on every rescan — Section 3.2 above) so the two schemes can never collide across a rescan. `addImageEntity`'s region-rebuild, which otherwise unconditionally replaces `regions`/`about` from a fresh EXIF read, preserves any existing standoff region whose name does *not* also appear among the freshly-parsed EXIF regions (and merges its name into the returned `people`/`pets` arrays, so a routine full `rocphotos scan` never silently un-facets it); one whose name *does* now appear among them is dropped, along with its body-proxy entity, on the understanding that the fresh EXIF-derived region is now the more authoritative copy of the same fact. `removeImageEntity` deletes a standoff region's body-proxy alongside the region itself, for the same reason. A caller that mutates the crate this way without re-reading the file at all (`/faces/confirm`'s standoff path) keeps the SQL index in sync via `syncImageIndexFromCrate` (`scanImage.js`) — the same entity/facet-sync logic `rescanImageMetadata` already runs after an actual file read, factored out so both paths share it exactly.

`ro_crates.id` and `entities.ro_crate_id` use this same crate-entity-id convention (`./` for the root, `<path>/` for a sub-crate), rather than a raw directory path, so that `ro_crates.id`, `entities.ro_crate_id`, a crate's own `entities.id`, and `entities.member_of` all agree for the same crate — every relationship is traceable by matching ids directly (including in the `export-excel` workbook), and the root crate is never a blank cell. `ro_crates.path` separately keeps the real, raw directory path for filesystem purposes (`.` for the root, never blank either).

AROCAPI requires a `metadataLicenseId`/`contentLicenseId` and access flags on every entity; since this application has no licensing or access-control model yet, a fixed placeholder license id is used -- the application MUST only serve data on a local port.

The index is populated via Node's built-in `node:sqlite` module (no native dependency) from the command line; a browser-side equivalent (backed by an in-memory WASM SQLite build, loaded from and saved back to the same physical file via the File System Access API) is planned but not yet implemented, so building the index is currently a CLI/desktop-mode-only operation.

A companion command, `rocphotos export-excel <directory>`, dumps the index to a three-sheet `.xlsx` workbook (RO-Crates, Entities, Files), for manual review without any SQL knowledge required. A further `--include-entity-crates` option adds a fourth sheet with each entity's full, resolved RO-Crate JSON-LD document (its own "mini crate", per AROCAPI — the same document `GET /entity/{id}/metadata` below returns), including EXIF detail that has no column of its own in the Entities sheet; this makes the workbook much larger and is meant for debugging, not routine review.

#### AROCAPI Endpoints and the Web View

A read-only AROCAPI request handler serves the index: `GET /capabilities`, `GET /entities` (filterable by `entityType`, `memberOf`, and the facet fields, as query parameters), `GET /entity/{id}`, `GET /entity/{id}/metadata` (an entity's full, resolved JSON-LD document, as above), `GET /files`, `GET /file/{id}` (the actual image bytes), `GET /ro-crates`, `GET /ro-crate/{id}` (with its materialised entity ids), `GET /ro-crate/{id}/metadata` (that crate's `ro-crate-metadata.json`, served verbatim), and `POST /search` (filters plus a list of requested facets, returning matching entities and, for each requested facet, its value/count breakdown). An id that itself contains `/` (nearly every entity and file id does) is passed as a single, percent-encoded path segment. There is no write/deposit support: every crate is still created and updated only by scanning, never through this API.

A companion `GET /entity/{id}/thumbnail` route, not part of AROCAPI itself, serves an entity's thumbnail bytes (resolved from its crate data, the same way `/entity/{id}/metadata` is), so the web view below can load a small preview per image rather than the full-size original.

This handler is written as a pure function of a SQLite driver and a filesystem adapter, with no HTTP or browser dependencies of its own, so the same handler can be reused by more than one transport. Today, `rocphotos serve <directory>` (desktop mode; see Section 4.1) hosts it over plain `node:http`, bound to `127.0.0.1` only, under `/api/*`, alongside a small static web view (`webview/`) that queries `/api/search` to browse and facet-filter the collection by camera, lens, keyword, rating, people, pets, and year, showing thumbnails and a full-screen viewer for the original image. A "Collections" panel above the facets lists every sub-crate (`GET /ro-crates`) as a directory tree — built by splitting each crate's id on `/`, so an intermediate directory with no crate of its own is shown only as a grouping label, not a clickable row — and clicking one sets the existing `memberOf` filter to scope the grid to that directory; an "All collections" button clears it. This is a plain filter like any other facet, just presented as a tree instead of a flat list. The viewer also fetches the entity's own full metadata (`GET /entity/{id}/metadata`) to show its keywords and depicted people/pets as clickable tags — clicking one applies it as a facet filter and returns to the grid — and, when the photo has any named face or pet region, a "Show faces" button that overlays each one's recorded bounding box with its name. The same fetch also drives a small metadata line (camera and lens, combined the same way the `camera`/`lens` facets themselves are, plus pixel dimensions) and a clickable date breadcrumb in the top-left corner ("2024 › 09 › 03", built from `dateCreated`) — clicking any segment closes the viewer and filters the grid to that year, year+month, or year+month+day, always replacing whichever of month/day was previously active rather than layering on top of it. `year` is the existing facet; `month`/`day` are plain date-part filters with no sidebar breakdown of their own (`filters.month`/`filters.day` in `buildSearchQuery`, `src/core/db/store.js` — `substr(date_created, 6, 2)`/`substr(date_created, 9, 2)`), meaningful only alongside `year` (a bare month would otherwise span every year). The breadcrumb reads year/month/day out of fixed string offsets rather than parsing `dateCreated` as a `Date`, so a future photo with only a year or year+month known (e.g. from an old scanned negative) degrades to a shorter breadcrumb instead of showing a bogus month/day — not yet exercised by any real data, since every current source of `dateCreated` (EXIF `DateTimeOriginal`) always supplies a full date, but deliberately not assumed by this code. Prev/Next buttons and the left/right arrow keys step through whichever result set (or collection) was on screen when the viewer was opened, in the same order the grid renders it, via the same `currentEntities` list "Select All" already uses. The same handler is also hosted from inside the browser-tab mode (Section 4.1), via a Service Worker (`src/sw.js`) intercepting same-origin `/api/*` `fetch` calls, so the exact same `webview/` files work there too, without any server process. The Service Worker cannot itself obtain a directory handle (there is no user gesture in that context), so the main page hands it the one `showDirectoryPicker()` already granted, via `postMessage` (`FileSystemDirectoryHandle` is structured-clone safe across that boundary); the Service Worker persists it in IndexedDB so it survives being independently restarted by the browser, and re-derives its own filesystem adapter and SQLite driver from it on the first request after each restart, rather than depending on any in-memory state surviving. If access has not been re-granted since last time (a Service Worker cannot itself prompt for permission), or the collection has not been scanned yet, `/api/*` requests get a clear JSON error explaining which, rather than failing silently.

### 3.3 Thumbnails

Operating system thumbnail caches (for example, Windows `Thumbs.db`, macOS Finder/QuickLook previews, or the freedesktop.org thumbnail cache on Linux) are not used as a source of thumbnails. These caches are stored outside the directory tree granted to the application via the File System Access API, are not portable with the crate, and in some cases use undocumented or proprietary formats.

Instead, the application generates its own thumbnails at the time a sub-collection crate is created or rescanned, skipping generation for a source file whose modification time has not changed since it was last processed (see Section 3). In the browser SPA this uses the Canvas API; the command-line tool generates thumbnails equivalently using an image-processing library (`sharp`), since no browser Canvas is available there. Either path may occasionally be unable to produce a thumbnail for a given format; when that happens, the image is still added to the crate, the failure is recorded in the RO-Crate (and not retried unless the file changes), and its generated pages fall back to displaying the full-size image. Thumbnails are stored in a `thumbnails/` subdirectory within each sub-collection crate directory, so that they are visible to the user in the filesystem, travel with the crate, and are listed as `hasPart` files of the crate. One thumbnail size is generated by default (for example, 400 pixels on the longest edge, encoded as JPEG); additional preview sizes may be added in future without requiring a change to this data model.

### 3.4 HTML Preview Pages

At scan time, the application writes a static `ro-crate-preview.html` file into every crate directory, alongside its `ro-crate-metadata.json`.

- In a sub-collection crate directory, the preview page is a thumbnail grid of every image the crate contains. Each thumbnail's caption shows the image's filename, its date (when known), any recorded EXIF extraction error, and — where EXIF data was extracted — a small metadata table wrapped in a collapsed `<details>` element, so the full EXIF listing is available without cluttering the grid.
- Clicking a thumbnail does not navigate to the raw image file directly; instead it opens a full-screen, in-page viewer showing the full-resolution image sized to fit the screen, with the same EXIF table available to expand, and a control to close it. This viewer is implemented in pure HTML and CSS (no JavaScript), so it works identically whether the page is served or opened directly via the `file://` protocol.
- In the root crate directory, the preview page provides date-based navigation: sub-collection crates are grouped into collapsible sections by year, then by month, and sorted chronologically (most recent first), each leaf entry linking to that sub-collection's own preview page. Only the most recent year, and its most recent month, are expanded by default; this keeps a collection spanning many years or decades manageable rather than presenting one long flat list. A sub-collection's representative date is the earliest EXIF date among the images it contains, not any naming convention of its directory path. Sub-collections with no dated images are listed separately under an "Undated" heading. Additional finding aids (for example, by subject or by camera) may be added in future without changing this data model.
- In the degenerate case where the root directory itself directly contains images (see Section 2), the root's preview page is a thumbnail grid, as for a sub-collection crate, rather than date-based navigation.

All relative links between generated pages, and from a generated page to an image or thumbnail file, are built as complete relative paths with every path segment percent-encoded, so that they resolve correctly under the `file://` protocol regardless of special characters (spaces, `#`, `?`, `%`, etc.) present in real filenames or directory names.

These pages are regenerated in full on every scan or rescan and are not treated as part of the crate's own metadata graph.

Each source photo's `ImageObject` entity is linked to its corresponding thumbnail `ImageObject` entity using the Schema.org `thumbnail` property, following standard Schema.org convention.

### 3.5 Future Features

A future release will have:

- `POST /search`'s write-side counterpart (deposits) is deliberately out of scope: crates are, and should stay, created and updated only by scanning.
- Further constructs such as events (weddings, festivals, parties) and arbitrary contextual descriptions around the collection, extending the facet set the same way camera/lens/keyword/people did. Person and Pet entities, extracted from identified face/pet regions in image metadata, already exist (Section 3.2).
- A face-crop thumbnail per person (using the bounding box already recorded — see Section 3.2 — to crop a small preview from the full image), rather than only a labelled box drawn over the full photo.
- Writing an edit back to the original image's own embedded metadata, not just the crate — see the Editing section above — pending a decision on the backup mechanism (Section 2's `_rocphotos/backup`).
- Face recognition is now implemented — see the Face Recognition section above. Pet recognition is not: the library used for faces (face-api.js) is exclusively a human-face model (detector, landmarks, and recognition net all trained only on human faces), so it cannot be pointed at pets — a pet auto-tagger would need an entirely separate model and pipeline, not an extension of the current one.
- A general-purpose manual tagger: select an arbitrary region of interest on a photo (a drag-to-draw box, not an automatically detected one) and label it with any free-text tag, rather than being limited to the Face/Pet regions MWG's own Type enum allows — for tagging an object, a place within the photo, or anything else the Person/Pet model does not cover.
- An RO-Crate MASP ("Machine Actionable Schemas and Profiles", as used in [collection2crate](https://github.com/Language-Research-Technology/collection2crate)) for this photo collection structure, to be authored once a representative set of example crates has been produced by the application.

## 4. Implementation Basics

### 4.1 Application Type

The application is a single-page application (SPA) that executes in three modes:

1. Entirely within the Google Chrome browser: no server-side component, with file access via the File System Access API. All processing, including file access, metadata extraction, RO-Crate manifest generation, and building the SQLite index (via `sql.js`, SQLite compiled to WASM — the exact same physical file format `node:sqlite` writes, so a collection indexed by either can be opened by the other), is performed client-side. After scanning, a link opens the same `webview/` view the CLI's `serve` command hosts (Section 3.2), backed here by a Service Worker rather than a real server. This mode's own initial screen (`index.html`/`src/main.js`, before any directory is opened) is called **Settings / Find Photos**: a Settings section (currently: "Always process everything on open", a per-machine `localStorage` preference; and "Write recognized faces back into photo files", a per-collection setting — Section 3.1 — disabled until a directory is open, since only then is there a `rocphotos.config.json` to read/save it against) above a Find Photos section (the "Open Directory" button and, once a directory is chosen, the sub-collection overview tree used to pick what to scan). It is the only settings surface in the whole app; `rocphotos serve`'s own web view (modes 2/3) has none, since every setting so far lives in the collection's own config file rather than needing a per-session control.
2. As a long-running local process, started from the command line and left running, that serves the AROCAPI web view (Section 3.2) plus its HTTP endpoints, over `127.0.0.1` only, opened in a normal Chrome tab. This is a second, separate frontend from mode 1's scanning SPA, sharing the same underlying index and crates — including, now, mode 1's own sub-collection overview/scanning screen (Section 3's Application Behaviour), bootstrapped automatically if this directory has never been scanned at all, rather than requiring a `rocphotos scan` CLI run first. This mode shares its implementation with the command-line tools (mode 3) rather than being a separately packaged native application.
3. As a set of command-line tools (`rocphotos scan`, `rocphotos export-excel`, `rocphotos export-album`, `rocphotos serve`) for scanning directories, building the SQLite index, exporting it for review, and serving it (mode 2), with full, unrestricted filesystem access via Node.js.

### 4.2 File System Access

The application accesses the local file system through the browser's File System Access API. The user selects a root directory via a directory picker, and the application is granted a handle to that directory for the duration of the session. All read and write operations, including the creation and updating of `ro-crate-metadata.json` files and any associated photo or thumbnail files, are performed against this directory handle. No files are uploaded to a remote server.

### 4.3 Technology Stack

- **Language:** JavaScript (ES modules).
- **Build tooling:** Vite, consistent with the build framework used by the [collection2crate](https://github.com/Language-Research-Technology/collection2crate) project.
- **RO-Crate handling:** The [`ro-crate`](https://www.npmjs.com/package/ro-crate) npm package (source repository [`ro-crate-js`](https://github.com/Language-Research-Technology/ro-crate-js)) is used for construction, parsing, and validation of RO-Crate metadata.
- **Target runtime:** Google Chrome (or other browsers implementing the File System Access API). No support for legacy browsers is required.

### 4.4 Architecture Constraints

- The application does not depend on any backend server or database outside of what it manages itself: persistent state is limited to the contents of the selected directory, the RO-Crate metadata files it contains, and the SQLite index described in Section 3.2 — all stored inside that same directory tree, not in any separate service or external database. The SQLite database is jsut an index - it can always be regenerated from scratch.
- Where the application does run a server (mode 2 in Section 4.1), it is bound to `127.0.0.1` only: a single-user, local convenience layer, never reachable from another machine.
- The application does not transmit photo files or metadata to any external service.
- The application operates on a single directory tree selected by the user at the start of a session.
- Every writer of a crate's `ro-crate-metadata.json` — the AROCAPI handler's own `/edit/*` routes and the faces handler's `/confirm` route alike — reads the current file, modifies an in-memory copy, and writes the whole thing back; none of them update it in place. Two such writes touching the same crate directory, issued close enough together to overlap (not merely two requests arriving close together, but genuinely still in flight at once — e.g. confirming two different people from the same batch review screen in quick succession, since neither request waits for the other to finish), can otherwise race: both read the same "before" state, and whichever finishes writing last silently discards the other's change. Confirmed as a real cause of data loss (two people tagged from the same photo batch, only one actually persisted) and fixed with a single, process-wide write queue (`src/core/writeQueue.js`'s `serializeWrites`) both handlers' write routes go through, so the whole process only ever has one crate-writing operation in flight regardless of which route or how close together the requests arrive. A personal, single-user app never needs these to run concurrently, so serializing them costs nothing worth noticing.

### 4.5 Testability and Filesystem Abstraction

Core operations, including directory traversal, crate boundary detection, EXIF extraction, and RO-Crate metadata construction, are implemented as pure functions decoupled from the browser's File System Access API. These functions depend only on a minimal filesystem adapter interface (directory listing, file reading, file writing), so that they are unit-testable and can be exercised from the command line via a Node.js implementation of the adapter with full, unrestricted filesystem access, in addition to the browser implementation used by the SPA. This allows the crate-building logic to be developed and verified without a browser, and reused unmodified inside the browser application.
